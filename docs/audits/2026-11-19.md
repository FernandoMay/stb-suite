## Hallazgo P0 compartido: bootstrap sin autorización

Las tres funciones públicas `initialize(admin, ...)` comprueban que la instancia no esté ya inicializada, pero no ejecutan `admin.require_auth()` antes de guardar el administrador/resolver/proveedor.

Esto deja una **ventana de first-call takeover para cualquier instancia nueva que aún no haya sido inicializada**: la primera cuenta que invoque la función puede intentar fijar las direcciones privilegiadas. La bandera `initialized` evita una segunda inicialización, por lo que esto **no demuestra compromiso de las instancias existentes que ya fueron inicializadas**. La evidencia histórica registra inicializaciones, pero no pude releer el estado actual de roles en Testnet.

**Gate:** proteger el bootstrap con autorización de la dirección admin propuesta o un mecanismo de despliegue/constructor que fije la autoridad de forma segura; probar invocación autorizada y no autorizada y cerrar la ventana deploy→initialize. Antes de redeploy, leer los roles de las instancias existentes.

## ¿SÍ O NEL?

### IMPLEMENTADO
- `create_prediction` autentica al creador.
- `submit_prediction` autentica al participante y permite una participación por wallet.
- `close_prediction` requiere autenticación del caller, permite creador/admin y exige `now >= closes_at`.
- `resolve_prediction` autentica al resolver global y persiste `total/correct/incorrect/points`; suma 10 puntos por acierto.
- El contrato mantiene lista de participantes para acreditar stats al resolver.

### PENDIENTE / riesgos
- Rotar resolver A→B puede bloquear la resolución de predicciones que guardaron snapshot A: `resolve_prediction` exige que el resolver global vigente coincida con el snapshot. Hace falta una política explícita para pendientes (mantener resolver anterior autorizado, migrar o cancelar).
- El `evidence_hash` solo comprueba longitud de 32 bytes y no-cero. En la evidencia E2E, el digest se calcula sobre un texto de prueba generado por el propio flujo; eso demuestra compromiso de bytes, no autenticidad de una fuente externa.
- `scripts/deploy-testnet.sh` ignora fallo de compilación con `|| true`, con riesgo de desplegar WASM anterior.
- `scripts/initialize-testnet.sh` imprime el comando de inicialización; no lo ejecuta ni verifica el resultado.

## TÓMBOLA

### IMPLEMENTADO
- El contrato define cliente Soroban para el oracle VRF: `request(context, requester)`, `is_fulfilled`, `get_beta(request_id)`, `request_round(request_id)`.
- El contexto incluye raffle ID, cierre y número de participantes, se fija antes del request.
- El beta que alimenta la selección proviene de `get_beta(vrf_request_id)`; no se observó uso de timestamp, ledger sequence, transaction hash ni seed elegido por organizador como aleatoriedad en el camino inspeccionado.
- `MockVrf` está declarado dentro de `#[cfg(test)]`, no en runtime.

### BLOCKERS críticos
1. **Fallback sesgado:** `derive_winner_index` prueba rejection sampling y re-deriva con SHA-256 hasta ocho intentos, pero si todos se rechazan acaba devolviendo `last_chunk % participants_len`. Esto reintroduce sesgo de módulo en una ruta posible. El test actual prueba el rechazo de un chunk `0xFFFFFFFF` para n=3, pero no prueba el caso de agotamiento de todos los chunks/intentos. No cumple el requisito de aleatoriedad sin sesgo en todas las rutas.
2. **Provider binding roto:** cada raffle guarda `randomness_provider`, pero `request_randomness` y `fulfill_randomness` leen `verifier` global mutable. Una rotación puede hacer que una raffle solicite/lea datos en un oracle distinto del snapshot guardado.
3. **Estado prematuro:** `create_raffle` establece `verifiable=true` antes de request/fulfill. Debe reflejar aleatoriedad verificada y resultado concluido, no una promesa.

## Wallet, frontend y scripts compartidos

- Los tres servicios usan Stellar Wallets Kit/Varial configurado con `Networks.TESTNET`, cliente Soroban con passphrase Testnet y `signAndSend()` para las escrituras. Esto es una ruta de firma/envío real en el código, pero no sustituye un E2E fresco.
- `getNetwork()` existe, pero no se comparó explícitamente el passphrase/red reportado por la wallet antes de cada escritura; `assertTestnetConfig()` valida variable de entorno y contract ID, no la red efectiva reportada por la wallet.
- `txHashFromSent()` puede devolver cadena vacía si las dos formas esperadas de hash no vienen en la respuesta; los callers no rechazan explícitamente ese caso.
- Los helpers de mutación devuelven hash/resultado tras `signAndSend()`, pero no ejecutan por sí mismos una lectura post-confirmación que afirme el postcondition esperado.
- Los hooks de enumeración usan `Promise.all`, pero convierten cada lectura fallida en `null` y omiten el registro. Un error RPC puede aparecer como hueco/registro inexistente.
- SI ignora un fallo de build con `|| true`. TÓMBOLA y BANDERA despliegan el WASM ya existente bajo `target` sin forzar build previo. Los scripts de inicialización no ejecutan ni verifican la transacción; SI imprime el comando, TÓMBOLA además mantiene nota de proveedor mock.

## Anti-mock / hardcodes

- Los repos privados no están indexados por GitHub Code Search (`is_code_search_indexed=null`). Las búsquedas para `Math.random`, `DEMO_MODE`, `MockVrf`, `fake/simulated/TODO/FIXME` devolvieron cero resultados, pero no se puede afirmar cobertura exhaustiva.
- En los contratos inspeccionados, no vi `Math.random` ni fuente pseudoaleatoria basada en timestamp/ledger/hash para TÓMBOLA. Su fuente implementada es `get_beta(request_id)` del oracle configurado. El problema no es usar un seed débil: son el fallback sesgado, el binding global mutable y la falta de revalidación independiente del proveedor actual.
- `MockVrf` está limitado a `#[cfg(test)]`; no se encontró en la sección runtime del contrato.
- Los contract IDs y el ID del VRF fijados en configuración son valores de despliegue, no por sí solos mocks. El drift de README/scripts sí crea riesgo operativo.

Fuentes técnicas de referencia:
