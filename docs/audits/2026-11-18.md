## Suite-wide P0 — unprotected contract initialization

All three current `contracts/src/lib.rs` files expose an `initialize` function that checks only whether the instance is already initialized, then stores the caller-supplied role addresses. None calls `admin.require_auth()` (or otherwise proves the proposed administrator's authority) before recording the admin and resolver/provider.

| Contract | Current finding |
|---|---|
| ¿SÍ O NEL? | `initialize(env, admin, resolver)` stores both addresses without authenticating `admin`. |
| TÓMBOLA | `initialize(env, admin, vrf_contract)` stores the admin and VRF provider without authenticating `admin`. |
| BANDERA ROJA | `initialize(env, admin, resolver)` stores both addresses without authenticating `admin`. |

**Impact:** on any new or still-uninitialized instance, a first caller can attempt to win the initialization race and select the role addresses. Passing an address as a function argument is not proof of that address's consent. This finding does **not** establish that any existing Testnet instance has been taken over; current stored roles were not read in this run.

**Required fix before any redeploy/new instance:** authenticate the proposed admin during bootstrap, or use a constructor/deployment flow that establishes authority atomically. Test unauthorized first initialization, authorized initialization, replay, and deployment/initialization race handling. For existing instances, independently read current role storage and inspect the original initialization transaction before deciding whether migration or redeployment is needed.

The three `initialize-testnet.sh` scripts are command-printing stubs, not executable initialization flows. TÓMBOLA's stub explicitly says “proveedor mock, verifiable=false,” contradicting the current README's real-VRF claims.

## Frontend, wallet, and deployment review

- All three frontends configure Stellar Wallets Kit/Varial for Testnet and generate Soroban clients using the Testnet passphrase. State-changing commands call `signAndSend()`; current Stellar SDK documentation says `signAndSend` submits and waits for network confirmation. That supports a real signing/submission path, but does not prove these specific deployed UIs completed each product flow. See the [Stellar JS SDK invoke guide](https://developers.stellar.org/docs/build/smart-contracts/getting-started/invoke-contract) and [SDK RPC reference](https://stellar.github.io/js-stellar-sdk/module-rpc.Server.html).
- `getNetwork()` exists, but the inspected write-client path does not explicitly compare the connected wallet's returned network/passphrase before each write. Keep the SDK Testnet config, but enforce the live wallet network at the write boundary.
- `txHashFromSent()` returns an empty string if neither supported hash field is present; callers do not reject an empty hash. Make a real non-empty transaction hash a required postcondition.
- Write helpers return the transaction result/hash, but no common helper performs and records an explicit post-confirmation read of the expected contract state. Query invalidation or a later UI refetch is not equivalent to an evidence-pack assertion.
- Per-ID enumeration catches RPC errors and returns `null`, then filters the record out. This can make a failed read look like a nonexistent record. Surface and count read errors instead of silently omitting them.
- Wallet refresh catches and suppresses errors. Add observable error state/logging appropriate for the UI.
- All three Netlify files use Node 20, `npm run build`, `dist`, and an SPA redirect. The repository settings specify Testnet in all three; only BANDERA ROJA has the contract-ID mismatch noted above.
- SiOnel's deploy script uses `stellar contract build ... || true`, which can allow deployment to continue after a failed build. TÓMBOLA and BANDERA deploy scripts use an already-built WASM path and do not themselves guarantee that the artifact was freshly rebuilt from the audited source. Make deploy fail closed and bind source commit to WASM hash/deploy tx.
- The three initialization scripts only print CLI commands; they do not execute initialization or verify the resulting roles/state.
