## Executive result

No functional commits have landed since 9 Nov 2026. The latest commits in all three repositories are UI/CTA changes. The most important new finding is a **shared bootstrap authorization flaw**: all three contract `initialize` functions accept admin (and resolver/provider) addresses without requiring authorization from the supplied admin. A first caller can therefore claim the roles on a fresh, not-yet-initialized instance. Treat this as a P0 blocker for any new deployment/redeployment and independently inspect the current roles stored in each existing instance.

No new transaction was submitted and no current Testnet state was independently read during this audit. Historical transaction records remain historical evidence, not fresh verification.

## Cross-suite findings

### P0 — all three initializers lack admin authorization

In each current `contracts/src/lib.rs`, `initialize(env, admin, resolver/provider)` checks only whether the instance was initialized, then writes the supplied role addresses. It does **not** call `admin.require_auth()` (or otherwise verify the supplied admin). The first successful caller of a fresh instance can therefore select the admin and resolver/provider addresses.

The separate `initialize-testnet.sh` scripts in all three repositories only print an example CLI command; they do not execute initialization or provide an atomic, race-free deployment/bootstrap operation. The source deploy scripts deploy an already-built WASM and are separate from initialization. For ¿SÍ O NEL?, the deploy script also uses `stellar contract build ... || true`, so a build failure does not stop the script before it attempts to deploy the existing WASM artifact.

**Impact:** this is not proof that an already initialized Testnet instance was taken over. Existing initialization transactions are recorded in project documentation, but current on-chain role storage was not read in this run. It is a critical source-level defect for fresh deployments and a reason to revalidate the admin/resolver/provider state of existing instances before relying on them.

Soroban's authorization model only creates authorization-tree nodes where the contract calls `require_auth`; the supplied address itself is not proof of consent. See the [Stellar composable auth model](https://stellar.org/blog/foundation-news/stellars-composable-auth-model) and [OpenZeppelin's Soroban access-control guidance](https://docs.openzeppelin.com/stellar-contracts/access/access-control).

### Shared frontend / wallet findings

- The inspected `stellar.ts` files use Stellar Wallets Kit with Varial and a Testnet network passphrase; writes are assembled through the generated Soroban client and `signAndSend()`.
- `assertTestnetConfig()` checks the configured environment value and non-empty contract ID. The inspected helper does not compare the connected wallet's reported network/passphrase immediately before every write. `getNetwork()` exists, but the wallet refresh path only stores its result.
- `txHashFromSent()` returns an empty string when neither response shape contains a hash. Write helpers do not fail closed on an empty hash.
- Enumeration hooks use `Promise.all`, but each per-ID rejection is converted to `null` and filtered out. This prevents one failed read from breaking the page, but silently hides unreadable records instead of distinguishing a gap/RPC error from a genuinely absent record.
- Wallet refresh catches and suppresses errors. RPC/indexer failures can consequently be under-reported.
- The write helpers await `signAndSend()` and expose a hash, but the helpers themselves do not assert a postcondition by reading the changed contract state after confirmation. Some UI pages invalidate React Query caches; that is not a substitute for a recorded, explicit post-write state assertion in the evidence pack.

The three repositories are not code-search indexed in the GitHub connection used for this audit. A search returning no matches would not be an exhaustive scan. The inspected TÓMBOLA `MockVrf` implementation is inside `#[cfg(test)]`; it is test-only, not part of the contract runtime. No statement of absolute absence of all mock/fake/placeholder strings is made.

## Next three priorities

1. **P0 — secure bootstrap across all three contracts.** Add explicit authorization of the proposed admin during initialization (or use a constructor/controlled deployment flow that proves authority), eliminate the unprotected deployment-to-initialize race, make build scripts fail closed, then inspect current Testnet admin/resolver/provider storage before any redeployment or trust decision.
2. **P0 — finish TÓMBOLA's randomness guarantee.** Use the provider snapshot for both request and fulfill or freeze verifier rotation while raffles are pending; remove the terminal modulo fallback; make `verifiable` reflect actual successful proof retrieval; reconcile README/init script/evidence transaction IDs; independently verify the deployed VRF WASM, keys, request/round/beta and winner on Testnet.
3. **P1 — close product correctness and evidence.** BANDERA ROJA: fix the Testnet contract ID in `netlify.toml`/README, persist correct/points (or remove the misleading persisted ranking fields and define a genuinely indexed derived leaderboard), and align vote documentation as on-chain. ¿SÍ O NEL?: define safe resolver rotation for pending predictions and complete a two-wallet create/participate/close/resolve/stats E2E. For all three: reject empty tx hashes, validate wallet network before writes, and include explicit post-confirmation state rereads.
