## Findings

### ¿SÍ O NEL?

Current contract:
- creator authorization on create/submit;
- explicit close only by creator/admin after `closes_at`;
- resolver is admin-controlled;
- creation snapshots the global resolver;
- resolution authenticates the global resolver and rejects if it differs from the creation snapshot;
- scoring is persisted: `total/correct/incorrect/points`;
- zero evidence is rejected.

Important nuance: resolver rotation is intentionally protected by `WRONG_RESOLVER`; an already-created prediction becomes unresolvable after rotation. This is not a bypass, but it is a lifecycle/governance blocker that needs an explicit migration/cancellation policy.

Netlify configuration is consistent with the real contract ID and `testnet`.

### TÓMBOLA

Current contract implements:
- external VRF interface;
- request ID persisted per raffle;
- drand round and beta persisted;
- context commits raffle ID, close time, and participant count before requesting randomness;
- no runtime `Math.random`, timestamp, ledger sequence, organizer seed, or transaction hash as randomness;
- MockVrf is under `#[cfg(test)]`.

Critical blocker remains:
`derive_winner_index()` performs rejection sampling but, after eight rejected attempts, returns `last_chunk % participants_len`. This is a biased fallback and violates the strict randomness gate even if extremely improbable.

Second blocker:
`create_raffle()` snapshots `randomness_provider`, but `request_randomness()` and `fulfill_randomness()` load the mutable global `verifier`. A verifier rotation can therefore make the stored provider snapshot disagree with the provider actually used.

The frontend hardcodes the known VRF contract ID in `DRAND_VERIFIER`; this is a duplicated configuration value, not a randomness source, but should ideally be reconciled with runtime contract state.

### BANDERA ROJA

Current contract clearly separates:
- `submit_vote()`: public on-chain vote;
- `submit_prediction()`: separate on-chain prediction;
- `publish_result()`: winner derived from frozen on-chain counts;
- canonical result hash reproducible from the snapshot;
- `calculate_score()`: returns 100/0 from prediction vs winner.

But `Stats.total` is incremented on prediction and `Stats.correct/points` are not persisted by `publish_result()`. The score is therefore derived per query, not persisted as ranking state.

Configuration:
- `netlify.toml` contains the correct contract ID and `VITE_STELLAR_NETWORK=testnet`.
- README still contains an incorrect StellarExpert contract link and a placeholder/incorrect `VITE_CONTRACT_ID` example. This is documentation drift, not proof of a live deployment mismatch.
