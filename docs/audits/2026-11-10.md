### VERIFICADO EN TESTNET

Historic deployment/initialization/create evidence is documented in the repository README. No new transaction was independently replayed during this run.

### PENDIENTE / BLOCKERS

- Resolver rotation remains a lifecycle hazard: a prediction snapshots the resolver at creation, while resolution requires the snapshot to equal the current global resolver. Rotating the resolver can therefore strand an already-created pending prediction.
- `evidence_hash` is only required to be non-zero/32-byte shaped; the contract does not bind it to an externally verifiable artifact.
- Fresh two-wallet Testnet evidence is still required for create → participate → close → resolve → stats, including post-confirmation rereads.

## TÓMBOLA

### IMPORTANT CURRENT FINDING

The current contract source is substantially more complete than the stale README text suggests.

Current `contracts/src/lib.rs` implements:

- per-raffle `vrf_request_id`;

### PENDIENTE / CRITICAL

1. **Provider snapshot binding is still incomplete:** `create_raffle` stores `randomness_provider`, but request/fulfill read the current global `verifier`. A verifier rotation can therefore diverge from the per-raffle snapshot.
2. **Extreme fallback still uses modulo:** after all rejection-sampling attempts are exhausted, `derive_winner_index` returns the final chunk modulo `n`. This reintroduces modulo bias in the stated extreme path. Under the product requirement, the safe behavior should be fail/continue with an unbiased derivation, not return biased modulo output.
3. The README is internally stale/contradictory: it still describes `fulfill_randomness` as a “mock local” and shows an obsolete `verifiable=false` model, while the current contract implements the VRF request/beta path. This documentation must be reconciled before external review.
4. The configured VRF oracle has not been independently audited here for operator/key trust, deployment, and current Testnet behavior beyond the repository's recorded E2E evidence.

## BANDERA ROJA

### IMPLEMENTADO

Current contract code clearly separates:

- `submit_vote`: on-chain vote, one per wallet, updates counts;
- `submit_prediction`: separate on-chain prediction;
- `close_poll`: creator/admin only after close time;
- `publish_result`: resolver-authenticated call with no resolver-supplied winner; winner is derived from stored vote counts;
- canonical result hash from the frozen poll/count state;
- `calculate_score`: reads 100/0 based on prediction vs winning option.

The frontend has separate signed wallet commands for vote and prediction.
