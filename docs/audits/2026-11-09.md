## ¿SÍ O NEL?

### IMPLEMENTADO

The current contract and frontend code contain real create, participate, close, resolve and stats paths. The contract requires authorization for creator, participant, closer, admin resolver rotation, and resolver resolution. The prediction stores a resolver snapshot and the contract checks that the snapshot still equals the global resolver before resolution.

The frontend write path uses the connected wallet through Stellar Wallets Kit and `signAndSend()`, and extracts the transaction hash.

### TESTEADO

The repository contains Rust tests covering the full local flow, duplicate participation, invalid evidence, unauthorized close, resolver rotation, close timing, repeated close/resolve, and other state guards. These are local contract tests and are not equivalent to a live wallet/Testnet replay because they use Soroban test utilities such as `mock_all_auths()`.

### VERIFICADO EN TESTNET

Historic Testnet deployment/initialization/create evidence remains recorded in the project documentation, including contract `CDOIAYBUTI2MQEUC6CJJYCIRPVKJDLVDIN56MU3ALMXO7IRRQNV2ACYT` and previously reported transaction hashes. This audit did **not** independently re-execute the lifecycle or establish a new transaction hash.

### PENDIENTE

- Evidence hash is syntactically a 32-byte SHA-256-shaped value and non-zero, but the contract does not cryptographically bind that hash to an artifact. A resolver can submit any non-zero hash.
- Resolver rotation remains a lifecycle hazard: a pending prediction snapshots the old resolver and later requires the global resolver to equal that snapshot. Rotation can therefore strand pending predictions.
- Need fresh two-wallet Testnet evidence for create → participate → close → resolve → stats, including resolver authorization and post-confirmation reads.

## TÓMBOLA

### IMPLEMENTADO

The current runtime path is not a simple `Math.random()` or timestamp selection. The contract requests randomness from a configured VRF contract, stores the request ID per raffle, checks fulfillment, obtains `get_beta(request_id)`, obtains the associated drand round, stores the randomness, and derives the winner from participant state.

The request context is committed before the result is known and includes raffle ID, close timestamp and participant count.

The frontend writes use the same real wallet signing path as the other apps.

### TESTEADO

Local Rust tests include request-ID association across raffles and winner derivation, but the tests use a local `MockVrf`. That is acceptable as a unit-test double but is **not** evidence that the production VRF oracle is genuine or available on Testnet.

### PENDIENTE / CRITICAL

Two code-level issues remain critical:

1. **Provider binding mismatch:** `create_raffle` snapshots the verifier into `randomness_provider`, but `request_randomness` and `fulfill_randomness` read the current global `verifier`. If the admin rotates the verifier after a raffle is created, the raffle's snapshot and the verifier actually used can diverge. The intended per-raffle provider binding is therefore not enforced end-to-end.
2. **Biased extreme fallback:** rejection sampling is used correctly for accepted chunks, but after all eight derived attempts are rejected, the code returns the final chunk modulo `n`. That fallback reintroduces modulo bias. Under the stated requirement, this should fail safely or continue with an unbiased derivation rather than return a biased result.

The configured VRF address is `CD5K4NNYNG3ZFCET24F3SL6MSYYRD5I2BSWW5K3LFQVIKYHRY2ICVIVX`. This audit has not independently verified the oracle's deployment, operator/key trust model, drand quicknet binding, or a fresh request→fulfill Testnet transaction.

## BANDERA ROJA

### IMPLEMENTADO

The current contract explicitly separates `submit_vote` from `submit_prediction`. Votes update on-chain counts and voters; predictions are stored separately and increment prediction stats. `publish_result` derives the winner from on-chain vote counts rather than accepting a resolver-supplied winner. The result hash is derived from a canonical payload. `calculate_score` compares the stored prediction with the resolved winning option.

The frontend exposes separate write commands for vote and prediction and uses the wallet signing path.

### TESTEADO

Local Rust tests cover vote counting, duplicate votes, invalid options, timing, deterministic tie handling, minimum votes, separation of abstention/prediction from voting, and score calculation. These are local tests and do not prove a fresh Testnet lifecycle.

### PENDIENTE / BLOCKERS

- `calculate_score()` returns a score but the inspected contract path does not persist `correct` or `points` into `Stats`; `submit_prediction` only increments `Stats.total`. Therefore a persistent ranking based on those aggregates is not proven complete.
- The README still contains contradictory language describing voting as off-chain, while the current contract and frontend implement on-chain voting. This documentation should be corrected before external review.
- **Netlify configuration currently contains a contract-ID typo:** `netlify.toml` has `CA53OBINI3BRK22ZWN2CDGB4FQ7QPNW5MH74ZLSHIBIQ35KF5RWBEBOR`, while the repository's documented/deployed contract is `CA53OBINI3BRK22ZWN2CDGB4Q7QPNW5MH74ZLSHIBIQ35KF5RWBEBOR`. This should be treated as a release blocker until the deployed site's environment is checked and corrected. No claim is made here about the live Netlify site's current value.
- Fresh Testnet evidence for vote + prediction + close + publish + score/ranking is still required.
