## ¿SÍ O NEL?

Current contract implements:
- creator-authenticated creation;
- participant-authenticated prediction;
- one participation per wallet;
- close only by creator/admin after `closes_at`;
- resolver set/rotated by admin;
- resolver snapshot on creation;
- resolver authorization on resolution;
- persistent total/correct/incorrect/points (+10 correct).

The remaining design edge is intentional but strict: after resolver rotation, old predictions whose snapshot differs from the current resolver cannot be resolved. This must be either prohibited by governance or resolved with an explicit migration/authorization rule.

Evidence hash is validated as non-zero 32-byte data but is not itself proof of an external artifact.

## TÓMBOLA

The contract now stores request ID, drand round, randomness and provider per raffle, and the test suite checks request-ID association across two raffles.

However, `derive_winner_index()` still has this final path after rejection-sampling attempts: `last_chunk % participants_len`. That is not acceptable under the project's absolute unbiased-randomness requirement.

More importantly, `create_raffle()` snapshots the verifier into `randomness_provider`, but `request_randomness()` and `fulfill_randomness()` read the mutable global verifier. A verifier rotation can therefore make the stored provider snapshot differ from the provider actually queried.

The README currently claims “rejection sampling” and “VRF verified on-chain”, but the code does not satisfy the no-fallback requirement. Documentation must be reconciled with code and deployed WASM.

## BANDERA ROJA

The current contract is clear and correct about architecture:
- `submit_vote()`: public on-chain vote, one per wallet;
- `submit_prediction()`: separate on-chain prediction, immutable;
- `publish_result()`: result derived from frozen on-chain vote counts;
- canonical SHA-256 result hash is reproducible;
- `calculate_score()`: derived 100/0 score.

But `Stats.total` is persisted at prediction time and `Stats.correct/points` are not updated by `publish_result()`. Thus a persistent on-chain ranking cannot currently be claimed as complete.
